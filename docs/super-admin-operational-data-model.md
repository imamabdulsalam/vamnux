# VAMNUX Super Admin Operational Data Model

**Designed:** 20 August 2026

The initial Super Admin expansion separates operational configuration from supplier catalog data. Supplier product records continue to preserve supplier identifiers and base prices; Admin configuration layers add storefront category navigation, product visibility, customer display-price history, exchange-rate policy, managed storefront content, and manual sync history without ever storing supplier credentials.

| Model | Purpose | Owner-only actions | Customer-facing effect |
|---|---|---|---|
| `marketplace_categories` | Managed VAMNUX category catalogue, ordering, visibility, SEO, and optional image reference | Create, edit, archive, order, feature | Active categories can power navigation and category landing content after public consumption is switched on |
| `product_admin_attributes` | VAMNUX product flags and editable metadata independent of supplier payload | Visibility, featured/trending/new/deal flags, SEO, internal notes | Only public-safe status/flags may be consumed by the storefront; internal notes never leave the server |
| `price_change_history` | Append-only before/after customer-price changes and reasons | Record generated by protected price mutations | No direct customer access; supports auditing and price investigations |
| `exchange_rates` | Manual base/quote rate and optional buffer configuration | Create/update/manual activation | Readiness only until a price-conversion policy is explicitly approved; storefront display conversion stays separate |
| `site_content_blocks` | Managed hero, banner, FAQ, announcement, and curated-list blocks | Create/edit/publish/archive with review state | Only published public blocks may render in the storefront |
| `supplier_sync_runs` | Manual supplier catalog sync history and outcome counts | Start/record approved manual runs | Provides truthful Admin health/history; does not schedule or trigger automatic synchronization |

## Integrity and safety rules

All configuration mutations require the existing server-side Super Admin gate, an explicit confirmation in the interface for consequential changes, and append-only audit events. Product/customer/supplier records remain distinct. A category or content configuration record does not invent inventory. A sync history record does not imply a supplier operation took place unless the corresponding server-side sync action completed.

The model deliberately does not yet include payment captures, refunds, digital-code storage, automatic promotions, referral credits, loyalty points, reseller credentials, scheduled jobs, payment-provider secrets, or supplier ordering. Those require their own approved business rules and external integration tests.
